# [MySQL 一行记录是怎么存储的？](https://xiaolincoding.com/mysql/base/row_format.html)

> 来源：小林Coding

## 存储文件结构

MySQL 数据存储在 `datadir` 目录（默认 `/var/lib/mysql/`），每个数据库对应一个目录，表文件包括：

| 文件 | 作用 |
|------|------|
| `db.opt` | 数据库默认字符集和校验规则 |
| `表名.frm` | 表结构（元数据） |
| `表名.ibd` | 表数据和索引（独占表空间） |

### 表空间结构层次

```
表空间 (Tablespace)
  └── 段 (Segment) - 数据段、索引段、回滚段
        └── 区 (Extent) - 1MB，连续 64 个页
              └── 页 (Page) - 16KB，最小 I/O 单位
                    └── 行 (Row) - 实际记录
```

## InnoDB 行格式

InnoDB 提供 4 种行格式：

| 行格式 | 说明 |
|--------|------|
| **Redundant** | MySQL 5.0 之前，古老格式 |
| **Compact** | 5.0+ 引入，紧凑格式，5.1 默认 |
| **Dynamic** | 5.7+ 默认，基于 Compact 改进 |
| **Compressed** | 基于 Compact，支持压缩 |

## COMPACT 行格式结构

| 变长字段长度列表(逆序) | NULL值列表(逆序) | 记录头信息 | 👇 指针位置 | 真实数据(正序) |
|:--------------------:|:---------------:|:----------:|:----------:|:-------------:|
| 🔴 向左读：元数据     |                 |            |            | 🟢 向右读：数据 |

> **核心设计**：`next_record` 指针指向记录头信息和真实数据之间的位置
> - **向左读**：获取记录头信息 → NULL值列表 → 变长字段长度列表
> - **向右读**：直接获取 row_id → trx_id → roll_ptr → 列1值 → 列2值 → …
>
> **完整字段顺序**：
>
> | 变长字段长度列表 | NULL值列表 | 记录头信息 | row_id | trx_id | roll_ptr | 列1值 | 列2值 | 列3值 | ... |
> |:---------------:|:----------:|:----------:|:------:|:------:|:--------:|:-----:|:-----:|:-----:|:---:|
> | 🔳 | 🔳 | 🔳 | 🔴 | 🔴 | 🔴 | 🟢 | 🟢 | 🟢 | 🟢 |

### 1. 变长字段长度列表

- 存储 VARCHAR、TEXT、BLOB 等变长字段的实际占用字节数
- **按列顺序逆序存放**（提高 CPU Cache 命中率）
- 若字段最大字节数 ≤ 255，用 1 字节表示；否则用 2 字节
- NULL 值的变长字段不记录长度

> 💡 **为什么逆序？**
>
> 逆序配合"中间指针"设计，使**列的长度信息**与**列的真实数据**在物理内存上尽可能靠近。这样可以利用 **CPU Cache 的空间局部性原理**：
>
> - CPU 按 Cache Line（通常 64 字节）读取内存
> - `col1长度`（指针左边最近）+ `col1数据`（指针右边最近）→ 极大概率在同一 Cache Line
> - 读取 `col1` 时，CPU 一次内存访问就能同时获取长度和数据，无需再次访问慢速内存
>
> 如果是正序，`col1长度` 离 `col1数据` 最远，反而离 `col3数据` 最近，毫无意义。
>
> 💡 **为什么不是必须的？**
>
> - **变长字段**（VARCHAR/TEXT/BLOB）：长度不定，必须额外记录
> - **定长字段**（INT/CHAR）：长度固定（INT 永远 4 字节），无需记录 → 节省空间

### 2. NULL 值列表

- 用二进制位标记允许 NULL 的列：`1` = NULL，`0` = 非 NULL
- 按列顺序**逆序排列**
- 必须用整数个字节表示，不足高位补 `0`
- **所有字段 NOT NULL 时，此列表不存在**（可节省空间）

> 💡 **存在性机制：为什么 NULL 不存真实数据？**
>
> InnoDB 不会在"真实数据"区存 NULL 字符串，而是用专门的「NULL 值列表」记录：
> - **允许 NULL** → 每行必须分配这个"小本本"（至少 1 字节）
> - **强制 NOT NULL** → MySQL 收到保证书，直接砍掉整个列表
>
> **收益**：1000 万条数据 × 1 字节 = 约 10MB 空间节省
>
> 💡 **位图（Bitmap）结构**
>
> NULL 值列表使用位图，**1 bit 对应 1 个可为 NULL 的字段**：
>
> | 字段数 | 占用字节数 | 说明 |
> |:------:|:---------:|:------|
> | 1~8 个 | 1 字节（8 bit） | 刚好塞满 |
> | 9 个 | **2 字节（16 bit）** | 必须开启新字节 |
> | 20 个 | **3 字节（24 bit）** | 20÷8=2.5，向上取整 |
>
> **公式**：`字节数 = ⌈允许 NULL 的字段数 ÷ 8⌉`（向上取整）
>
> 💡 **实战建议**
>
> - 能写 `NOT NULL` 就写，并给默认值（如 `''` 或 `0`）
> - 避免 NULL 导致索引失效和 COUNT 计算复杂
>
> 💡 **为什么逆序？**
>
> 与变长字段长度列表同理，配合"中间指针"设计提高 CPU Cache 命中率。
>
> 💡 **建议**：字段设置 NOT NULL 可节省至少 1 字节（NULL值列表占用）

### 3. 记录头信息

| 字段 | 作用 |
|------|------|
| `delete_mask` | 标记记录是否被删除 |
| `next_record` | 下一条记录位置（链表组织） |
| `record_type` | 记录类型：0=普通，1=B+树非叶子，2=最小，3=最大 |

> 💡 **next_record 为什么指在"中间"？**
>
> 指向记录头信息和真实数据之间的位置，实现**数据和元数据的完美隔离**：
>
> | 方向 | 读取内容 |
> |:----:|---------|
> | → 向右 | 第一列、第二列、第三列…的真实数据 |
> | ← 向左 | 记录头信息、NULL值列表、变长字段长度列表 |
>
> 这样设计逻辑清晰：取数据向右，取描述向左。

### 4. 真实数据

包含用户定义字段 + 3 个隐藏字段：

| 隐藏字段 | 大小 | 说明 |
|----------|------|------|
| `row_id` | 6 字节 | 无主键/唯一约束时存在 |
| `trx_id` | 6 字节 | 事务 ID（必需） |
| `roll_pointer` | 7 字节 | 回滚段指针（必需，MVCC） |

## varchar(n) 最大值

### 核心概念

#### 1. 65535 字节限制

MySQL 规定：**一行记录的所有列（除 TEXT/BLOB 外）总长度不能超过 65535 字节**。

- 注意单位是**字节（Byte）**，不是字符
- 限制范围是**整行**：多个字段的字节数总和也不能超过 65535

#### 2. VARCHAR(n) 的 n 代表什么？

`VARCHAR(n)` 中的 **n 代表字符数**，而非字节数：

- "A" 和 "中" 都算 1 个字符
- 实际占用字节数由**字符集**决定：

| 字符集 | 单字符最大字节数 | 说明 |
|:------:|:---------------:|:-----|
| `ascii` | 1 字节 | 英文字母、数字 |
| `utf8` (utf8mb3) | 3 字节 | 旧版 MySQL 默认 |
| `utf8mb4` | 4 字节 | MySQL 8.0 默认，支持 emoji |

#### 3. 不可忽视的隐藏开销

为什么不能直接把 n 设为 65535？因为还要扣除**元数据开销**：

| 开销类型 | 计算规则 | 单字段允许 NULL 时 |
|:--------|:---------|:------------------|
| **变长字段长度列表** | 最大字节数 ≤255 → 1 字节；>255 → 2 字节 | 2 字节（极限情况） |
| **NULL 值列表** | 每 8 个允许 NULL 的字段占 1 字节 | 1 字节 |

> 💡 **实战技巧**：字段设为 `NOT NULL` 可节省 NULL 值列表的开销！

---

### 单字段极限值计算

**假设**：表只有 1 个 `VARCHAR(n)` 字段，允许为 NULL

**最大可用字节** = 65535 - 长度列表(2) - NULL 值列表(1) = **65532 字节**

**不同字符集的 n 最大值**：

| 字符集 | 计算公式 | n 最大值 |
|:------:|:---------|:--------:|
| `ascii` | 65532 ÷ 1 | **65532** |
| `utf8` | 65532 ÷ 3 | **21844** |
| `utf8mb4` | 65532 ÷ 4 | **16383** |

---

### 多字段通用公式

```
所有字段数据字节数总和 + 变长字段长度列表总字节数 + NULL 值列表总字节数 ≤ 65535
```

**示例**：3 个 `VARCHAR(100)` 字段，utf8mb4，允许 NULL

| 项目 | 计算 | 字节数 |
|:----|:-----|:------|
| 真实数据 | 3 × 100 × 4 | 1200 |
| 长度列表 | 3 × 2（每字段>255字节） | 6 |
| NULL 值列表 | 3 字段 < 8 | 1 |
| **总计** | | **1207** ✅ 远小于 65535 |

---

### 面试一分钟速答

> **"VARCHAR(n) 最大值取决于三个因素："**
>
> 1. **行总限制**：MySQL 规定一行所有列数据总大小 ≤ 65535 字节
> 2. **隐藏开销**：需减去变长字段长度列表（1-2 字节/列）和 NULL 值列表（1 字节起）
> 3. **字符集**：n 是字符数，ascii 最大 65532，utf8 最大 21844，utf8mb4 最大 16383 |

## 行溢出处理

当一行数据超过页大小（16KB）时，发生**行溢出**。

| 行格式 | 溢出处理 |
|--------|----------|
| **Compact** | 真实数据处存储部分数据 + 20 字节溢出页指针 |
| **Dynamic / Compressed** | 完全行溢出，只存 20 字节指针 |

## 常见面试题

### 1. MySQL 的 NULL 值是怎么存放的？

**答案**：

MySQL 的 Compact 行格式中会用「NULL 值列表」来标记值为 NULL 的列，**NULL 值并不会存储在行格式中的真实数据部分**。

- NULL 值列表会占用 1 字节空间
- 当表中所有字段都定义成 **NOT NULL**，行格式中就不会有 NULL 值列表，这样可节省 1 字节的空间

---

### 2. MySQL 怎么知道 varchar(n) 实际占用数据的大小？

**答案**：

MySQL 的 Compact 行格式中会用「**变长字段长度列表**」存储变长字段实际占用的数据大小。

---

### 3. varchar(n) 中 n 最大取值为多少？

**答案**：

**一行记录最大能存储 65535 字节的数据**，但是这个限制**包含**「变长字段字节数列表」和「NULL 值列表」占用的字节数。

所以计算 varchar(n) 最大值时，需要减去这两个列表占用的字节数：

**单字段示例**：表只有 1 个 varchar(n) 字段，允许为 NULL，字符集为 ascii

```
n 最大值 = 65535 - 变长字段长度列表(2) - NULL值列表(1) = 65532
```

**多字段情况**：要保证所有字段的长度 + 变长字段字节数列表 + NULL值列表 ≤ 65535

---

### 4. 行溢出后，MySQL 是怎么处理的？

**答案**：

如果一个数据页（16KB）存不了一条记录，InnoDB 存储引擎会自动将溢出的数据存放到「**溢出页**」中。

| 行格式 | 溢出处理方式 |
|:------|:-------------|
| **Compact** | 真实数据处存储**部分数据** + 20 字节溢出页指针 |
| **Dynamic / Compressed** | 完全行溢出，只存 **20 字节指针**指向溢出页 |

Compact 会保留部分数据在前 768 字节，剩余数据存溢出页；而 Dynamic/Compressed 则完全存溢出页，只留指针。
