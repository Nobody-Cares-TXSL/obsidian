# 安装来源与维护决策

本文件回答三个问题：程序从哪里来、有哪些版本并存、以后升级或替换时要注意什么。

## 安装渠道概览

| Cargo / Rustup | Alacritty 0.17.0 | cargo install / cargo update |
| cargo install --path（本地源码） | ~/.cargo/bin/tmux-expose | 见下方「tmux-workspace-expose」；2026-11-09 起为当前方式 |

## 需要留意的安装细节

### Alacritty

Cargo 0.17.0 由 Rustup 管理，APT 0.13.2 仍在系统中。GNOME 的 org.gnome.desktop.default-applications.terminal.exec 已设置为 Cargo 二进制绝对路径。APT 升级不会自动替换这个用户级 gsettings 值，但手动修改桌面入口时要保持一致。

### Yazi

Yazi / ya 位于 /usr/local/bin，不归 APT 管理。升级需要手动下载 GitHub Release 并替换二进制。必须同时维护配置目录和自定义插件，详见 [Yazi配置与预览系统](../04-%E6%96%87%E4%BB%B6%E7%AE%A1%E7%90%86%E5%99%A8/Yazi%E9%85%8D%E7%BD%AE%E4%B8%8E%E9%A2%84%E8%A7%88%E7%B3%BB%E7%BB%9F.md)。

### ueberzugpp

来自 OBS 仓库 home:justkidding，仓库地址：
http://download.opensuse.org/repositories/home:/justkidding/xUbuntu_24.04/

APT key 位于 /etc/apt/trusted.gpg.d/home_justkidding.gpg，有效期曾更新至 2028-08-14。该仓库由第三方维护，未来升级前先确认仓库和签名状态。

核对密钥时务必区分两种标识，它们是不同长度的不同值：

| 标识 | 值 | 用途 |
|---|---|---|
| Key ID（16 位） | AA6B2752759F9361 | 短标识，人工沟通时常见，可被碰撞 |
| 完整 Fingerprint（40 位） | 7627D0F8F60FBA35371A29E1AA6B2752759F9361 | 信任决策依据，正式核验以此为准 |

取法（40 位指纹在独立的 `fpr` 记录行，不在 `pub` 行）：

~~~bash
gpg --show-keys --with-colons /etc/apt/trusted.gpg.d/home_justkidding.gpg | grep '^fpr'
~~~

该 key 当前放在 trusted.gpg.d 且没有 signed-by 限定，信任范围较宽。严格做法是迁移到 /etc/apt/keyrings 并在源配置中使用 signed-by；这是维护候选，不是本次已完成的修改。

### Vim 变体与剪贴板

2026-11-08 安装 `vim-gtk3` 以获取 `+clipboard`，并用 `update-alternatives --config vim` 把候选从自动模式改为手动指向 `/usr/bin/vim.gtk3`。

- 三套二进制并存：`vim-tiny`、`vim`（提供 vim.basic）、`vim-gtk3`。只有 vim.gtk3 带 `+clipboard` 和 `+xterm_clipboard`。
- 切换候选同时影响 `/usr/bin/editor`、`vi`、`view`、`ex`、`vimdiff`、`gvim` 等一组 alternatives 链接，不只是 `vim` 一个名字。
- 连带安装 ruby3.2、libruby、rake、fonts-lato、liblua5.1-0 等约 46 MiB 新包；这些是 vim-gtk3 的编译依赖，不是用户主动选择的工具。
- APT 升级 vim-gtk3 时会重写二进制，但 alternatives 的手动选择（manual 状态）不会被重置回自动模式。
- 回滚：`sudo update-alternatives --config vim` 选 `vim.basic`；如不再需要图形版，`sudo apt remove vim-gtk3 vim-gui-common`，但注意别连带移除仍在使用的 vim 主包。

### unclebob 三件套（crapper / dryer / mutator）

代码质量工具，分别做 CRAP 复杂度评分、重复代码检测、变异测试。支持 Clojure、Java、Go、TypeScript、Rust、Python。

部署方式与普通工具不同，复现时注意：

| 项目 | 位置 |
|---|---|
| 源码仓库 | `~/.local/share/ub-tools/<工具名>/`，各自独立 git 仓库 |
| 上游 | `https://github.com/unclebob/<工具名>.git` |
| 命令入口 | `~/.local/bin/<工具名>`，三行 `exec` 包装脚本 |

首次运行会自动在源码目录建 `.venv` 并 `pip install -e .`，所以第一次执行明显慢，之后走本地虚拟环境。当前三个 `.venv` 均已创建。

依赖关系：mutator 要求 crapper 检出在相邻目录（`../crapper`），因为函数名和 namespace 从 crapper 读取。单独升级或移动其中任何一个都会破坏这个关系。

升级方式：在各仓库内 `git pull`。没有包管理器介入，不会随 APT 或 npm 更新。

### tmux-workspace-expose（工作区预览）

上游 `cesarferreira/tmux.expose` 的二开版本，2026-11-08 发布为公开仓库 `https://github.com/Nobody-Cares-TXSL/tmux-workspace-expose`，首个二开提交 `eb54bd3`。保留上游提交历史与 MIT 许可，版本号从 0.1.0 重新开始（与上游 0.8.0 无关，不要按号大小比较新旧）。发布时移除了上游的 crates.io 发布流程、未使用的 Session 时间字段和两个无调用的辅助函数，因此**不在 crates.io 上**，只能从仓库安装。

#### 为什么这个插件装完还要"部署"一次

多数 tmux 插件（如 resurrect、continuum）是一堆 shell 脚本，TPM `git clone` 完就能跑。**这个不是。** 它由两部分组成，更新方式互不相干：

| 部分 | 内容 | 谁负责更新 |
|---|---|---|
| 插件脚本 | `tmux.expose.tmux`，负责读配置、绑键、启动程序 | TPM：`Prefix + U` |
| 可执行程序 | Rust 编译产物，负责画总览、算缩略图、写状态 | 自己：`cargo build` 后复制到 PATH |

TPM 只会 `git clone`，克隆下来的是 `src/*.rs` 源码，**不含任何可执行文件**（插件目录里没有 `target/`，也没有二进制）。tmux 跑不了 Rust 源码，所以入口脚本第 63 行是这样找程序的：

~~~bash
command="${command:-tmux-expose}"   # 读 @tmux-expose-command，没有就回退到 PATH
~~~

推论有三条，都是实际踩过的：

- **只做 `Prefix + U` 不会更新程序本身**。2026-11-09 就出现过这个状态：插件脚本已到 43a570e，但二进制还是 11-08 编的旧版，修复不生效。
- **只换二进制不同步插件脚本**，则配置项和键位绑定可能对不上。
- **两者都没有时**，Alt + e 会报 command not found——插件"装好了"、配置也对，但按了没反应。

判断当前跑的是哪一版，不能看插件目录的 HEAD，要看二进制身份：`--version` + 文件 mtime + MD5。

#### 一个项目四种名字

这是本机最容易搞混的地方：

| 层面 | 名字 | 依据 |
|---|---|---|
| Cargo 包名 | tmux-workspace-expose | Cargo.toml name |
| 库名 | tmux_expose | Cargo.toml [lib] name |
| 构建产物 / 安装命令名 | tmux-expose | Cargo.toml [[bin]] name |
| 本机实际部署名 | tmux-expose | `~/.cargo/bin` 下的文件名（2026-11-09 前曾是 `~/.local/bin/tmux-expose-workspace`） |

`--version` 输出为 `tmux-workspace-expose 0.1.0`，与旧的 `tmux-expose 0.8.0` 可以据此区分。

本机加载项和旧版备份如下。

| 副本 | 内容 | 状态 |
|---|---|---|
| ~/.tmux/plugins/tmux-workspace-expose/ | fork，HEAD 43a570e（与源码树一致） | **活动**，TPM 加载这份的 tmux.expose.tmux |
| ~/.cargo/bin/tmux-expose | 二开版 0.1.0（cargo install 安装） | **活动二进制**，tmux 与 Claude Code hook 都指向它 |
| ~/.local/bin/tmux-expose-workspace | 二开版 0.1.0（手工构建副本） | 迁移后不再被引用，保留作回滚 |
| ~/.local/state/tmux-expose-legacy.xKLFCF/ | 上游插件目录、0.8.0 二进制和 Cargo 安装记录 | 清理前备份 |

~/.tmux.conf 第 74–75 行现状：

~~~tmux
set -g @tmux-expose-command '/home/duan/.cargo/bin/tmux-expose'
set -g @plugin 'Nobody-Cares-TXSL/tmux-workspace-expose'
~~~

原先直接 `run-shell` 源码树入口脚本的那一行已删除，改由 TPM 加载 fork。**风险已消除**：之前记录的"运行二进制来自未提交工作树、clone 无法复现"不再成立——源码目录 `~/Project/Code/tmux-plugin/tmux.expose`（目录名仍是旧名）remote 已指向 fork，`git status` 干净。

**三个位置各有自己的版本标识，必须分开看**（2026-11-09 部署后实测）：

| 位置 | 版本标识 | 状态 |
|---|---|---|
| 源码树 / 远端 main | 43a570e — fix: 修复 Agent 状态残留与写入报错 | 已推送，工作区干净 |
| TPM 加载的插件副本 | 43a570e | 已更新，与源码树 `src/`、入口脚本、Cargo.toml 逐字节一致 |
| 实际运行的二进制 | MD5 `e09c223f…`，mtime 2026-11-09 01:23 | 已部署，与构建产物一致 |

三者现在对齐。**这个"三处对齐"是靠一次人工操作达成的，不是自动同步**——将来任何一处单独变动都会重新产生偏差。判断"部署的代码到底是哪一版"不能只看 HEAD，要看产物身份：`--version` 输出 + 部署文件 mtime + MD5。三处的更新动作也各不相同：源码树 `git pull`，TPM 副本 `Prefix + U`，二进制重新构建后复制部署。

### Agent 状态修复（43a570e，已部署）

| 修复 | 旧行为 | 新行为 |
|---|---|---|
| 写入失败返回码 | `set_pane_option` / `clear_pane_option` 用 `let _ = ...status()` 吞掉一切，退出码恒 0 | 合并为 `tmux::write_agent_status()`，检查 `output.status.success()`，失败时把 tmux 的 stderr 一并报出来 |
| 僵尸徽标挤占排序 | 已退出的 Pane 仍保留 `@agent_status`，继续参与排序 | 写入时额外记 `@agent_status_pane_pid`（`set-option -pF ... '#{pane_pid}'`）；读取时用 tmux format 判断 `pane_dead` 或 `pane_pid != @agent_status_pane_pid` 就忽略该徽标，`respawn-pane` 后也不会继承上一个进程的标记 |

过滤条件是这一行 format：

~~~tmux
#{||:#{pane_dead},#{&&:#{@agent_status_pane_pid},#{!=:#{pane_pid},#{@agent_status_pane_pid}}}}
~~~

**仍然没解决的边界**：如果只有 Agent 退出、外层 Shell 还活着，`pane_pid` 不变，标记不会被自动忽略，仍需手动 `agent-status clear`。文档里那条"陈旧标记影响排序"的说明对这种情况依然成立。

部署后逐项实测（当时用 `~/.local/bin/tmux-expose-workspace`，不是构建目录；迁移到 `cargo install` 后同样的验证在新路径上重跑过一遍，结果一致）：

| 场景 | 结果 |
|---|---|
| 非法状态参数 `bogus` | 退出码 1，报错并列出合法值（旧版返回 0） |
| 无效 Pane `%999999` | 退出码 1，带 `no such pane: %999999`（旧版静默返回 0） |
| 正常写入 `attention` | 三个选项都写入：`@agent_status`、`@agent_status_since`、`@agent_status_pane_pid` |
| `respawn-pane -k` 后 | pane_pid 从 562112 变为 562247，过滤表达式返回 **1**，旧徽标被忽略；旧标记仍留在选项里但不参与显示 |
| 连续两次 `clear` | 均返回 0，读回为未设置（幂等） |

旧二进制备份在 `~/.local/bin/tmux-expose-workspace.bak-20261109-012336`（MD5 `fe0148e0…`），回滚即复制回去。

测试数从 106 增至 **107**（lib 91 + bin 16），`make check` 通过，并在独立 tmux 会话验证了徽标显示、Pane 退出与重启、重复清除、无效目标报错。

**不要拿 `~/tmp/tmux-expose-target` 里的产物当持久证据。** 2026-11-09 核验时，为了跑本机测试和复现安装冲突，我用它作为 `CARGO_TARGET_DIR` 执行了 `cargo test --release` 与 `cargo install`，结果 `target/release/tmux-expose` 被重新编译覆盖，MD5 从 `fe0148e0…` 变成 `e68cfe50…`，与已部署副本不再相同。部署文件本身未受影响（mtime 和哈希都没变），但"部署产物与构建产物逐字节一致"这条证据链**已被一次常规构建操作销毁**，之后无法再复现比对。

原因是 Rust release 构建本身不保证跨 invocation 逐字节可复现：构建路径、profile 参数、`--release` 与 `cargo install` 的 flag 差异都会改变输出字节。所以这条证据只在"刚构建完、还没动过 target 目录"的窗口内有效。要留下可长期核对的身份信息，应该记 `--version` 输出 + 部署文件的 mtime + MD5，而不是指望临时 target 目录。

入口脚本在 `@tmux-expose-command` 缺失时会从 PATH 查找裸命令 `tmux-expose`。卸载旧版后，本机 Shell 已找不到这个裸命令。保留 `@tmux-expose-command` 和 hook 中的绝对路径。

**隔离构建环境**：`CARGO_HOME=~/tmp/tmux-expose-cargo`（57 MiB）、`CARGO_TARGET_DIR=~/tmp/tmux-expose-target`（实测 767 MiB，2026-11-09）。两者都在 $TMPDIR 下，会被系统清理；由于源码已发布，重建没有障碍，只是一次全量编译的时间成本。

#### 安装方式：2026-11-09 已从手工路径迁到 cargo install

迁移前有两条路并存，评估后选了官方路径。现在**只保留一条**，旧的手工方式仅作历史记录：

| 维度 | `cargo install`（现行） | 手工 `cargo build` + 改名（已弃用） |
|---|---|---|
| 更新 | **一条命令**：`cargo install --locked --force --path .` | 构建、复制、改名三步 |
| 卸载 | `cargo uninstall tmux-workspace-expose`，有 `.crates.toml` 记录 | 手动删文件 |
| 产物位置 | `~/.cargo/bin/tmux-expose`（PATH 第 1 位） | `~/.local/bin/tmux-expose-workspace`（PATH 第 7 位） |
| 与入口脚本默认值 | **一致**：脚本回退值就是裸名 `tmux-expose` | 不一致：必须保留 `@tmux-expose-command` |
| 构建隔离 | 共用默认 `CARGO_HOME` | 独立 `CARGO_HOME` |

迁移执行记录：

1. `cargo install --locked --force --path ~/Project/Code/tmux-plugin/tmux.expose`
2. 验证：`~/.cargo/bin/tmux-expose --version` → `0.1.0`；非法参数返回 1；三选项写入正常；respawn 后过滤表达式为 1；`clear` 幂等。
3. `.tmux.conf` 第 67 行改为 `~/.cargo/bin/tmux-expose`，`tmux source-file` 重载，`list-keys -T root` 确认三个入口（Alt+e / Alt+w / Ctrl+,）的 `-E` 参数都是新路径。
4. `~/.claude/settings.json` 5 处 hook 命令改为绝对路径新值（用字符串替换，未重新序列化 JSON；diff 验证 5 删 5 增，全部是路径行）。
5. 旧二进制 `~/.local/bin/tmux-expose-workspace` 保留未删，作回滚用。

三个实测细节值得记：

- **三种构建方式的字节各不相同**：`cargo install` 得 `2c62c522…`，隔离 `cargo build --release` 得 `e09c223f…`，早先一次 `cargo install` 得 `f72448d4…`。功能一致（同为 0.1.0），但**不能用哈希跨方式核对**。这是"Rust release 构建不保证逐字节可复现"的又一例证。
- **tmux server 的 PATH 第 1 位就是 `~/.cargo/bin`**（`tmux show-environment -g PATH` 实测）。所以现在即使删掉 `@tmux-expose-command`，入口脚本的裸名回退也能命中正确版本。
- **hook 仍写绝对路径而不是裸名**。虽然 tmux server 能解析裸名，但 Claude Code 的 hook 未必在同一个 shell 环境里执行，裸名有失效风险；绝对路径没有这个不确定性。

迁移需要同步的硬编码路径共 6 处：`.tmux.conf` 1 处、`~/.claude/settings.json` 5 处。前一处漏改会让 Alt + e 换版，后几处漏改会让状态写入静默失效。

README 的两种 `--path` 写法不矛盾，按所处目录区分：`git clone` 之后在父目录用 `--path ./tmux-workspace-expose`，进入项目目录更新时用 `--path .`。

如改用 README 中的 Cargo 安装路径，先安装二开版并核对 `--version`，再更新 tmux 和 hook 的引用。

### 从上游迁到 fork 时 cargo install 会失败（已复现）

包的 `[[bin]]` 名沿用 `tmux-expose`，与上游发布的同名二进制撞名。下面是不带 `--force` 的旧安装命令在目标已有同名文件时的报错。

~~~
$ cargo install --locked --path .

### Agent 状态诊断与清理

本机已配置五个 Claude Code hook，独立 tmux 会话已验证状态命令能写入和清除两个 Pane 选项。真实 Claude Code 会话的自动触发仍待验收。 [事件映射与验收步骤](../06-%E5%BC%80%E5%8F%91%E5%B7%A5%E5%85%B7%E9%93%BE/%E5%BC%80%E5%8F%91%E8%BF%90%E8%A1%8C%E6%97%B6%E4%B8%8EAI-CLI.md#claude-code-的-tmux-状态-hook)

总览先把每个 Session 内所有 Pane 的标记汇总为最高等级。开启 Agent 优先排序时，Session 按 `attention` → `waiting` → `working` → 无标记排列。同一等级内，当前 Session 放在其他 Session 后面，再按该等级最早的 `@agent_status_since` 排序。

**陈旧标记会影响排序。** `@agent_status_since` 是排序时间戳，代码没有 TTL 或进程存活检测。如果 Claude Code 异常退出、`SessionEnd` 没有执行而 Pane 仍存在，旧状态会保留到下次写入、手动清除或 Pane 关闭。一个非当前 Session 的旧 `attention` 若在同档最早，可能长期占据总览首位。

在残留状态所在的 Pane 运行下面三条命令。最后两条都应输出为空。第一条只清除状态，不关闭 Pane。

~~~bash
tmux-expose agent-status clear
tmux show-options -pqv -t "$TMUX_PANE" @agent_status
tmux show-options -pqv -t "$TMUX_PANE" @agent_status_since
~~~

**区分启动和写入。** 本机 hook 保留命令原始退出码，命令路径失效、不可执行或状态参数无效时仍会返回非零。各事件如何显示错误取决于 Claude Code，`StopFailure` 等事件会忽略 hook 退出码。命令启动后，`set_pane_option` 和 `clear_pane_option` 丢弃 tmux 子进程的结果，tmux 的 stderr 仍可能出现。缺少 `TMUX_PANE` 时命令也会直接返回成功。因此，用退出码检查命令失败，用目标 Pane 的选项读回确认状态是否写入。 [Claude Code hooks 退出码与事件行为](https://code.claude.com/docs/en/hooks#exit-code-output)

## 凭据安全现状

2026-11-08 实测的权限与配置事实（不记录密码值本身）：

| 文件 | 实测权限 | 问题 |
|---|---|---|
| ~/.zshrc | 644 | 同机其他用户可读；内含明文 DB_PASS |
| ~/.harlequin.toml | 664 | 其他用户可读、同组可写 |

Harlequin 连接本机 127.0.0.1:3306 时使用 **root 账号**，并设置 `read_only=true`。需要区分两件事：

- `read_only` 是 Harlequin 客户端行为，只约束这个 UI 不发写语句；
- MySQL 服务端仍然授予该账号全部权限。任何绕过客户端、直接用同一凭据连接的程序都能写入。

处置顺序（尚未执行，需逐项确认）：

1. 轮换数据库密码。
2. 把 DB_PASS 移出 ~/.zshrc，改为权限 600 的秘密文件或系统密钥管理，Shell 启动时按需读取。
3. `chmod 600 ~/.harlequin.toml`。
4. 为 Harlequin 建独立 MySQL 只读账号，用服务端权限而不是客户端开关来保证只读。

## 以后做选择的原则

1. 一次只替换一个层级，避免把终端、Shell、复用器和文件管理器混为一组变量。
2. 使用真实工作负载测试：同一目录、同一 tmux 布局、同一 Yazi 预览和同一个编码 Agent，逐条过上表。
3. 以响应速度、内存占用、启动开销、兼容性和维护成本为依据，不只看界面效果。
4. 优先保持配置可迁移，避免把工作流绑定到单一终端模拟器。
5. 升级前检查依赖、安装来源和回滚路径。
6. 记录“当前实际运行”而不是“曾经安装”。
